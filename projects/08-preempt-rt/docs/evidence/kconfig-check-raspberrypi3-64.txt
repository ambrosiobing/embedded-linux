This is the check the whole kernel side of Project 8 exists to pass.
CONFIG_PREEMPT_RT depends on EXPERT && ARCH_SUPPORTS_RT, and arch/arm64
gained that select in 6.12 while meta-raspberrypi scarthgap still defaults
to 6.6. On 6.6 the option is silently dropped and the board boots a kernel
that is not preemptible while the results table claims otherwise.

It supersedes kconfig-check-raspberrypi4-64.txt, which is the same check
against the machine this project was originally scoped for. That file is
kept unedited. The board turned out to be a Raspberry Pi 3 Model B v1.2,
the machine changed, and the prediction written into that file before this
rerun was: the paths change, the kernel version does not, because it comes
from PREFERRED_VERSION_linux-raspberrypi in kas/bench-rt.yml, and
ARCH_SUPPORTS_RT does not, because arch/arm64/Kconfig selects it for the
architecture rather than for the SoC. That is what happened.

Three facts had to line up, and each was checked separately:

  1. the version pin took            head -4 of the kernel's own Makefile
  2. every fragment line is a symbol  ./go ksym -f rt

Both checks below open by naming the tree they did NOT read. That line
exists because of what happened on the first attempt at this rerun: the
build host now holds one kernel tree and one .config per machine, both
checks were choosing their input with a lexical sort, and
"raspberrypi4-64" sorts after "raspberrypi3-64". So ./go ksym read the
abandoned machine's tree and reported 31 symbols all real, which was the
correct answer arrived at from the wrong file, because both trees were

A check that is right for the wrong reason is worse than one that fails.
The selection is now newest_path in scripts/common.sh, shared by five call
sites, and it names what it did not choose. See journal entry 35 and
decision 59. The stale raspberrypi4-64 tree was deliberately left in place

The four lines this file exists for:

    CONFIG_PREEMPT_RT=y
    CONFIG_PREEMPT_NONE off
    CONFIG_PREEMPT_VOLUNTARY off
    CONFIG_PREEMPT off

kernel/Kconfig.preempt declares those four inside a choice block, so
exactly one can be set and the other three are not merely absent, they are
excluded. Reading PREEMPT_RT=y alone would not establish that; reading all
four does. This is also why rt.cfg carries the three "is not set" lines
rather than only the one that is wanted: a fragment that asks for a member
of a choice without saying what it displaces is a fragment whose result
depends on the defconfig it lands on.

WHAT THIS DOES NOT PROVE

  - that the board booted this kernel
  - that /sys/kernel/realtime reads 1 on the board, which is criterion 1
  - any latency number

It proves that the configuration the board will be given is the
configuration that was asked for, on the machine the board actually is.
Everything after this is the build, the card and the wire.

To confirm it against the running kernel, once the board is up:

    scp root@BOARD:/proc/config.gz /tmp/ && zcat /tmp/config.gz > /tmp/config
    ./go kconfig -f rt /tmp/config

That is better evidence than this file, because a .config in a work
directory is what kconfig produced and /proc/config.gz is what the board
is running.
