# The three paths out of a sensor, measured

Saturday 24 October 2026, Raspberry Pi 3 Model B Plus, `bench-iio-image`
built from commit `8ae1ada`, kernel 6.6.63-v8, X-NUCLEO-IKS4A1 on the
40-pin header. Data in [`rates-2026-10-24.csv`](rates-2026-10-24.csv),
nine runs of five seconds each, taken with `iio-rate`.

These are the first rate measurements this project has taken under a Yocto
image with mainline drivers. Everything before them was on eplepi, the Pi
4B, with out-of-tree drivers compiled on the board.

## The settings are in this file and NOT in the CSV, which is a defect

The CSV records what happened and not what was asked for. Rows 4, 6 and 7
are identical in every column except `irqs`: same path, same device, same
460 samples per second, same 2304 samples. Nothing in the file says one
was watermark 64, one 32 and one 128. The two `poll` rows likewise differ
only in their outcome, with no column saying the first ran at 7.5 Hz and
the second at 960.

So the independent variables below were recovered from the session they
were typed in, which is exactly the fragility this repository warns about:
a results file that carries outcomes without conditions is not something a
second person can check. **`iio-rate` should write `odr_hz` and
`watermark` columns**, and until it does, a row in that CSV is only
interpretable beside a file like this one.

## The comparison the project exists to make

| Path | samples/s | interrupts/s | reader CPU |
|---|---|---|---|
| poll, 960 Hz | 61 | 0 | 58.8 % |
| hrtimer trigger, 100 Hz | 100 | 0 | 0.4 % |
| FIFO, 480 Hz, watermark 64 | 460 | 11.60 | 0.4 % |
| FIFO, 480 Hz, watermark 1 | 468 | 469.60 | 1.2 % |

The poll path delivers 61 samples a second for 58.8 per cent of a core.
The trigger path delivers more samples than that for 0.4 per cent. The
FIFO path delivers seven and a half times as many, also for 0.4 per cent.

Interrupts per second, reader CPU, and samples delivered against samples
asked for are the three figures comparable across all three paths. The
timestamp spread is not, and the tool refuses to present it as though it
were: see below.

## Criterion 3, the trigger path: MET

`iio-rate trigger lis2mdl 100 -d 5`, 501 samples in 5 s against 500
expected.

**Timestamp interval standard deviation 7.088 us, against a threshold of
100 us.** Source `iio-core`, so these are timestamps the IIO core applied
as it pushed each scan, and their spread is real kernel latency: hrtimer
wake-up, the I2C read, and the push into the buffer.

The magnetometer is the right device for this and was chosen before the
measurement rather than after it. It has no FIFO of its own, so there is
no hardware batching path to confuse the comparison with.

## Criterion 4, the hardware FIFO: MET

The criterion asks for interrupts per second and reader CPU with and
without a watermark, since the point is the difference between them.

| Watermark | samples/s | interrupts/s | reader CPU |
|---|---|---|---|
| 64 | 460 | 11.60 | 0.40 % |
| 1 | 468 | 469.60 | 1.20 % |

Same sample rate, **forty times fewer interrupts**, three times less CPU.
That is what a hardware FIFO buys and it is the project's central claim
about this path.

**The design document asks for 416 Hz and this part cannot do it.** The
LSM6DSV16X ladder is 7.5, 15, 30, 60, 120, 240, 480 and 960. 416 Hz was
written for a different sensor. 480 was used and `docs/DESIGN.md` needs
correcting rather than the measurement being bent to fit it.

## Why `iio-rate` says the interrupt count is wrong when it is not

Every batched run reports a `ratio` of measured interrupts over expected,
and every one of them is above 1.0. The tool computes `expected = rate /
watermark`. That formula is wrong for this driver family in two separate
ways, and the result is a tool that cries defect on correct behaviour.

### One: half the FIFO entries are timestamps

`drivers/iio/imu/st_lsm6dsx/st_lsm6dsx_buffer.c`:

```c
ts_sip = max_t(u16, ts_sip, sensor->sip);
sip   += sensor->sip;
hw->sip = sip + ts_sip;
...
fifo_watermark = (fifo_watermark / hw->sip) * hw->sip;
fifo_watermark = fifo_watermark * hw->settings->fifo_ops.th_wl;
```

With only the accelerometer enabled it is the only sensor, so `min_odr` is
its own rate, its `sip` is 1, `ts_sip` is 1, and **`hw->sip` is 2**: the
FIFO pattern is one accelerometer sample followed by one timestamp entry.
`th_wl` is 1 for this part, so the hardware threshold is counted in FIFO
entries and equals the watermark asked for.

An interrupt therefore arrives after **W/2** accelerometer samples, not W.
That is a factor of two the tool does not know about.

### Two: the drain is not instantaneous

W/2 is a floor, and the measurements sit above it by an amount that grows
with the output data rate. The interrupt fires when the FIFO crosses the
threshold; the threaded handler then reads the current level and drains
everything present, and the FIFO keeps filling during that I2C read.

Holding the watermark at 64 and moving only the rate:

| ODR | samples per interrupt |
|---|---|
| 120 Hz | 32.0 |
| 480 Hz | 39.7 |
| 960 Hz | 52.4 |

Samples per interrupt rises from 32 to 52 for an unchanged watermark. No
fixed arithmetic factor can do that, and it is the signature of time spent
draining.

**The relationship, derived and then checked rather than asserted.** If
the drain costs a time proportional to the number of samples drained, then
the samples delivered per interrupt S satisfies

    S = (W/2) / (1 - k * ODR)

One constant, fitted from a single run, 480 Hz with W=64: k is about 405
microseconds per sample. What matters is what it then predicts elsewhere:

| Run | predicted S | measured S |
|---|---|---|
| 960 Hz, W=64 | 52.3 | 52.36 |
| 480 Hz, W=128 | 79.4 | 79.45 |
| 480 Hz, W=32 | 19.9 | 19.04 |
| 120 Hz, W=64 | 33.6 | 32.0 |

Three of the four are close. The 120 Hz point sits at exactly 32.0, the
bare pattern floor with no surplus at all, which the model cannot produce
for a non-zero k.

**And 32.0 is itself a reading that needs care.** The run reports 17
interrupts and 512 samples, which is 30.1 per interrupt, below the floor
and therefore impossible. 512 over **16** interrupts is exactly 32.0. With
only seventeen interrupts in the window, one firing at the edge without
its samples being counted moves the figure by six per cent, and that is
the likeliest reading. The honest statement is that at 120 Hz the surplus
is at or near zero and the run is too short to say more; a longer run at
low rates would settle it.

k is a fitted constant from one point, not a measured quantity. It should
not be quoted as a property of this driver until it has been checked
against a different bus speed, which would move it if it is really I2C
time.

### What follows for the tool

`expected` should be `rate / (2 * watermark)` for this driver family, and
should be labelled a floor rather than an expectation, with the surplus
explained as drain time. As it stands, `iio-rate` reports a 1.2x to 1.8x
discrepancy on every batched run and invites the reader to go looking for
a fault that is not there.

## Two more small defects found while measuring

**The poll path's ceiling is the driver's power-up, not the bus.** At the
boot default of 7.5 Hz, `poll` managed 2 samples per second at 3.4 per
cent CPU: the reader was asleep, not busy. `st_lsm6dsx` serves a raw sysfs
read as a one-shot, powering the sensor up, waiting for it to settle at
the configured rate, reading, and powering it down. Setting the rate to
960 Hz moved it to 61 samples per second at 58.8 per cent CPU, a factor of
thirty, which identifies the settling wait as the cap. It does not explain
the remaining 16.4 ms per read, and that is open.

**The interrupt column matches the wrong part.** Every run prints `irq
line matching "lsm6" in /proc/interrupts`, including the `lis2mdl` trigger
run. The zero there is correct, since the hrtimer path has no hardware
interrupt, but the pattern is hardcoded to a part that was not being
measured, so the column would be wrong rather than merely empty if an
`lsm6` interrupt were firing for another reason.

## What this is not evidence about

No sample value has been checked. These runs count samples and interrupts
and measure CPU and timestamp spread; not one of them asks whether the
numbers coming out of the sensor are correct. Gravity has not been
measured, no axis has been identified, and the mounting matrix message in
`dmesg` means axes are reported in the sensor's own frame rather than the
board's.

The FIFO timestamp spread of 0.111 us is not a latency measurement and is
not comparable with the trigger path's 7.088 us. The driver assigns those
timestamps by interpolating backwards from the interrupt time using the
configured rate, so their tightness is the driver's arithmetic agreeing
with itself. `iio-rate` labels the source on every row for this reason and
refuses to print the comparison.
