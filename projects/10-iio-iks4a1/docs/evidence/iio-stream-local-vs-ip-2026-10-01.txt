CORRECTION AND RE-CORRECTION, Thursday 1 October 2026

THIS HEADER HAS BEEN WRONG ONCE ALREADY. READ BOTH PARAGRAPHS.

The section below headed "WHAT WAS SUBSTITUTED" says the accelerometer
timed out because the interrupt line delivered nothing, and that the
substitution to lis2mdl followed from it. A first correction withdrew that
and blamed an unset output data rate instead. THE FIRST CORRECTION WAS
WRONG AND THE ORIGINAL TEXT WAS RIGHT.

What settles it, measured the same evening:

  - with the wire off CN9 pin 6, iio-rate fifo gives 0 interrupts and 0
    SAMPLES, not fewer samples. The FIFO path is entirely interrupt driven.
  - with the wire on, the identical iio-stream commands return 201 lines in
    0.504 s at 480 Hz and 5 lines in 0.873 s at 7.5 Hz with a four-sample
    buffer.
  - sampling_frequency never reads 0 on st_lsm6dsx. After rmmod and insmod
    it reads 7.500000. The power-down premise was never checked before it
    was published.
  - 7.5 Hz with a four-sample buffer completes, so there is no timeout
    defect either.

Three mechanisms were proposed for one observation, in this order: power-
down, fill time against libiio's timeout, and a rate dependence. All three
were wrong, and what they were competing to explain was an unplugged wire
left in place after a control experiment.

So: the interrupt explanation in the text below stands, the substitution to
lis2mdl was forced by the bench, and the first correction is withdrawn. See
journal entry 51 for the full accounting.

Unaffected throughout: every number in this file, and the local-against-
remote comparison itself, which never depended on the accelerometer.

WHAT WAS SUBSTITUTED, AND WHY IT IS STATED HERE RATHER THAN GLOSSED

iio-stream defaults to lsm6dsv16x_accel and this measurement used lis2mdl.
That is a deliberate substitution and the criterion does not name a device,
but the reason has to be on the record.

The accelerometer was tried first and failed:

    root@eplepi:~# ./iio-stream -d lsm6dsv16x_accel -n 40 -b 256
    WARNING: High-speed mode not enabled
    refill failed: Connection timed out

The cause is the bench fault already documented against criterion 4, and
/proc/interrupts says so without ambiguity:

    185:   0   0   0   0   pinctrl-bcm2835  24 Edge   lsm6dsx

Zero on all four CPUs, including during the attempt that timed out. The
LSM6DSV16X has a hardware FIFO and its own interrupt, so st_lsm6dsx
registers a trigger of its own and the buffered path uses that rather than
any software trigger. With the interrupt line delivering nothing, that path
cannot complete a refill, and no software change reaches it.

The LIS2MDL has no hardware FIFO and takes a software trigger, which is why
criterion 3 was measured on it too, and for the same reason: it is the one
path the interrupt fault cannot reach.

So criterion 5 is met for the local-versus-remote property it is about, and
it is NOT evidence that the accelerometer streams over the network. That
needs the jumper fixed and is the same blocker as criterion 4's second half.

HOW THE FAULT HAS CHANGED CHARACTER, WHICH IS WORTH MORE THAN EITHER COUNT

Thursday 1 October 2026, morning:  IRQ 185 reached 100001, the kernel's
spurious-interrupt threshold, and the watchdog disabled the line.
Thursday 1 October 2026, evening:  IRQ 185 reads 0 after a reboot and a
reload, and the line delivers nothing at all.

Same jumper, same shield, same pin, opposite failure. A wire that both rings
and goes open is a connection problem rather than a threshold problem, which
is the argument for shortening it or adding series resistance rather than for
filtering in software.

THE ORDERING TRAP THAT COST THE FIRST REMOTE ATTEMPT

The first remote run connected, authenticated, enumerated and answered, and
listed only three devices:

    no device named lis2mdl in this context
    devices present:
      cpu_thermal
      rpi_volt
      sht4x

Those three are hwmon devices surfaced through libiio's hwmon backend. None
of the four IIO devices appeared, because iiod had been started by systemd
before the ST modules were insmoded and ENUMERATES ONCE AT STARTUP.
systemctl restart iiod fixed it.

This is guaranteed to bite anyone following the reload sequence in
RESUME.md, because that sequence loads drivers after boot and systemd starts
iiod at boot. The symptom reads as "the remote context cannot see my sensor",
which points at the network, and the fault is a stale service. The local run
was unaffected because iio-stream builds a fresh local context every time it
starts.

WHAT THIS DOES NOT SHOW

  - the accelerometer over the network, which needs the interrupt
  - anything about throughput: 100 Hz on three channels is not a load test,
    and the criterion does not ask for one
  - any claim about libiio 1.x, where iio_buffer_refill does not exist and
    this program would not compile. Both hosts here are 0.26, the last of
    the 0.x line
