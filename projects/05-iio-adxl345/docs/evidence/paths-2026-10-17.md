# What the paths cost, Saturday 17 October 2026

Two of the three ways out of this part, measured by Project 10's
`iio-rate` on the card flashed at `ff83351`, seventeen seconds apart.
The third, a trigger at a known rate, is in the last section and is not
measured here.

    iio-rate poll bench-adxl345 -d 10
    iio-rate fifo bench-adxl345 100 24 -d 10

| | polled | hardware FIFO |
|---|---|---|
| samples a second | 105 | 96 |
| interrupts a second | 0 | 4.00 |
| reader CPU | 94.00 % | 0.10 % |
| timestamps | none | driver-interpolated, sd 1566 us |

## The CPU column is the result

940 times, as measured. 859 times per sample once the small difference
in rate is divided out: 0.895 percent-seconds a sample polled against
0.00104 batched.

That is what the part's FIFO is for, and it is the first time this
project has put a number on it. The driver's own arithmetic says the
same thing from the other side: 92 interrupts a second saved, 24.0
samples per interrupt against one per sample.

**Two caveats, and the first one matters more than the number.**

`iio-rate` is a shell script, so 94 per cent is what a shell costs
reading a sysfs attribute in a loop, not what polling costs. A C program
reading the same file would be far cheaper, and the honest comparison
this row supports is "a shell reader against the kernel batching into a
buffer", not "polling against FIFO" in general. The instrument is part
of the measurement, which this bench has had to learn twice already.

The second: 94 per cent is of one core on a four-core board, read from
the reader's own `/proc` ticks over the elapsed time. It is a saturated
thread, not a saturated board.

## The polled arm reads faster than the part converts

105 polls a second against about 96 conversions, which was measured two
independent ways this morning. So roughly 9 reads a second, 9 per cent
of them, returned a conversion that had already been returned.

Nothing in the polled path can tell. There is no timestamp, no sequence
number and no data-ready check: the driver reads the output registers
whenever sysfs is read, and the part answers with whatever it last
converted. A reader that wants distinct samples has to rate-limit itself
or watch `DATA_READY`, and this one does neither because the attribute
it reads offers neither.

That is not a defect in the driver or in the tool. It is the property of
the sysfs path that the other two paths exist to fix, and it is visible
here only because the two arms were measured against each other.

## The timestamp column, and what it refuses to claim

`iio-rate` prints the FIFO arm's spread as 1566 us and labels it
`driver-interpolated`, with three lines saying it is not a latency
measurement. It is right to: the driver assigns those times by counting
back from the interrupt at the configured rate, so their spread is
arithmetic rather than observation.

The triggered path is the one whose timestamps are measured, by the IIO
core, when the trigger fires. Five of them were captured the same day in
`triggered-2026-10-17.md`, spaced 1.015 seconds apart by a shell loop
that slept one second.

## The third arm, and why it is not here

A trigger at a known rate needs `CONFIG_IIO_HRTIMER_TRIGGER`, which
lives in `iio.cfg` behind `BENCH_IIO_KERNEL`, and this project's kas
file sets only `BENCH_ADXL345_KERNEL`. The sysfs trigger that is in
every image fires when something writes to it, so it can prove the path
and cannot measure a rate.

What that costs to close: one line in `kas/bench-adxl345.yml`, a kernel
rebuild because the fragment changes the configuration, and a reflash.
Then `iio-rate trigger bench-adxl345 100` completes this table, and the
question the design document raises but nobody has answered becomes
measurable: what happens when the trigger asks faster than the part
converts, which is the same duplicate-sample problem the polled arm
shows at 9 per cent.
