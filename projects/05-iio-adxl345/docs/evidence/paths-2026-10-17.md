# What the three paths cost, Saturday 17 October 2026

The comparison `docs/DESIGN.md` has described since before this driver
existed, measured on one part, one card, one boot and one orientation.
The card is the image built at `9429c89`, which is the first to carry
`CONFIG_IIO_HRTIMER_TRIGGER` and the module to make a trigger with.

    iio-rate poll    bench-adxl345     -d 10
    iio-rate trigger bench-adxl345 100 -d 10
    iio-rate fifo    bench-adxl345 100 24 -d 10

| | polled | hrtimer trigger | hardware FIFO |
|---|---|---|---|
| samples a second | 102 | 100 | 96 |
| interrupts a second | 0 | 0 | 4.00 |
| reader CPU | 92.50 % | 0.40 % | 0.20 % |
| timestamp spread | none | 1.682 us | 1670.786 us |
| timestamps from | nothing | the IIO core | the driver's arithmetic |

Three facts fall out of the first row alone. The polled reader free-runs
at whatever rate it can issue reads, 102. The trigger sets the pace
exactly, 100. The FIFO delivers what the part converts, 96.

## The CPU column, and what it is really comparing

462 times between polled and triggered, 4 times between triggered and
FIFO.

The second of those is the interesting one, because both read six bytes
per sample over the same bus at nearly the same rate. The difference is
not traffic, it is wakeups: 100 a second against 4. The FIFO saves 24 of
every 25 and costs half the CPU.

**The first is not a comparison of polling against triggering.**
`iio-rate` is a shell script, so 92.50 per cent is what a shell costs
reading a sysfs attribute in a loop, forks and all. A C reader doing the
same thing would be far cheaper. What this row supports is a shell
reader against the kernel delivering into a buffer, and saying more than
that would be putting the instrument inside the result, which this bench
has done twice before and recorded both times.

## The timestamp column refuses a comparison on purpose

1.682 microseconds against 1670.786 is not a thousandfold difference in
jitter. The trigger figure is measured: the IIO core takes the time in
the hard interrupt half, as `iio_pollfunc_store_time`, and the spread is
real scheduling latency. The FIFO figure is computed: the driver assigns
times by counting back from one interrupt at the configured rate, so its
spread is the batch period and the oscillator, and the tool prints three
lines saying it is not a latency measurement.

## The run that measured the wrong path and said otherwise

Between those rows, one `iio-rate fifo` reported 984 samples, **zero
interrupts**, 0.10 per cent CPU and a spread of 1.483 microseconds,
labelled `fifo` and `driver-interpolated`.

Both labels were false. A trigger left attached by the tool's own
trigger path made the IIO core take the triggered route; this driver
leaves the part's FIFO in bypass on that path by design, so the samples
came from the leftover hrtimer. `/proc/interrupts` read `0 0 0 0` for
the whole boot, which is the fact that settles it.

It is kept in the CSV as `fifo-contaminated` because it is the evidence
for decision 124, and because a table of measurements that quietly drops
the wrong one is worth less than one that explains it. The tool now
detaches what it finds, and fails a FIFO run whose interrupt rate is
below half what the watermark predicts.

## The duplicate question, answered

`docs/DESIGN.md` says that a trigger asking faster than the part
converts re-reads one conversion, that neither the driver nor the core
reports it, and that it is a thing to measure. It was never measured
because no image carried a trigger with a rate.

Two captures of 201 scans each, counting consecutive scans whose x, y
and z are identical:

| trigger | scans | distinct | duplicates | |
|---|---|---|---|---|
| 200 Hz | 201 | 94 | 107 | **53.2 %** |
| 50 Hz | 201 | 190 | 11 | 5.5 % |

At 200 Hz against a part converting near 96, the rate ratio predicts
1 - 96/200, which is 52 per cent. Measured 53.2.

**The 50 Hz arm is the control and it measures what the method cannot
distinguish.** Below the part's rate every scan is a fresh conversion,
so those eleven repeats are two consecutive conversions of a motionless
sensor landing on identical bits. That floor is 5.5 per cent, and the
effect at 200 Hz is ten times it.

The 200 Hz capture also re-derives the part's output rate a third
independent way: 94 distinct conversions in the second it took, against
96 from the FIFO interrupt arithmetic and 96.7 from counting raw
interrupts the same morning. Three methods, 94 to 97 Hz, against the 100
the rate register asks for.

    dd if=/dev/iio:device0 bs=16 count=200 2>/dev/null | od -v -x |
        awk '{print $2" "$3" "$4}' | uniq -c | awk '...'

`od -v` is load bearing: without it `od` collapses repeated lines into
an asterisk, which is precisely what was being counted.

## The earlier card

The first two rows of the CSV were taken on `ff83351`, before any image
here had an hrtimer trigger. They agree with the `9429c89` rows to
within the noise, which is worth having: the kernel configuration
changed between the two cards and the driver did not, and the numbers
say so.
