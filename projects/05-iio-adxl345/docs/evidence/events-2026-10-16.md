# Tap and free fall events, Friday 16 October 2026

Criterion 6, measured on the Raspberry Pi 3B+ with image `e3574c8`,
`INT1` on GPIO23 level high, the bus at 100 kHz. The three lines in
`events-2026-10-16.csv` are `iio-events` output exactly as the board
printed it, while the bench surface beside the board was tapped.

| What arrived | Reading |
|---|---|
| two double taps | 188 ms apart, both on `IIO_MOD_X_OR_Y_OR_Z` as this driver reports them |
| one free fall | `thresh` `falling`, which is the code the handler pushes for `INT_SOURCE` bit 2 |
| no single tap | see below; this is a finding, not a gap in the run |

**One interrupt carried two events.** The second double tap and the free
fall share a timestamp to the nanosecond, which is correct rather than
suspicious: the handler reads the clock once per interrupt and pushes
every bit it finds set in `INT_SOURCE`, so two causes in one assertion
of `INT1` get one time.

**No single tap appeared, and the hardware is why.** A double tap is
reported on its own line by the part, and with the single tap function
also enabled a sharp knock that satisfies both produces the double tap
only, because `INT_SOURCE` carries the double tap bit for the second of
a pair. The run did not test single tap in isolation. Doing that means
clearing the double tap enable first, and it is worth doing before the
criterion is called complete in every direction.

## The caveat that has to travel with these numbers

**The bus was failing intermittently during this run.** Writes to the
event attributes returned `EREMOTEIO` and then `EIO` between two
otherwise identical attempts, which is the I2C no-acknowledge this
breakout has produced before: it failed entirely at 400 kHz on Friday
9 October 2026 and works at 100 kHz on six jumpers and two straps into
a breadboard. The events above arrived on the same wiring minutes after
a write to it failed.

So these three lines prove the path end to end, from the part's own
detection through `INT1`, the threaded handler, the IIO event FIFO and
the character device to a program that needs no libiio. They do not
prove anything about how often an event is missed, and the first thing
to fix before counting events is the wiring, not the driver.

## The register dump taken afterwards changes how to read all of this

Half an hour after the run, with the driver unbound, `DATA_FORMAT` read
`0xaf` and a dump of `0x1d` to `0x39` showed more:

| Register | Held | Should hold |
|---|---|---|
| `DATA_FORMAT` 0x31 | `0xaf`, so SELF_TEST, INT_INVERT and Justify set | `0x0b` |
| `OFSX` `OFSY` `OFSZ` | `0xa9` `0xba` `0x7a`, up to 1.9 g of trim | zero |
| `BW_RATE` 0x2c | `0x07`, 12.5 Hz | `0x0a`, 100 Hz |
| `INT_ENABLE` 0x2e | `0xba`, data ready, activity and inactivity on | only what is asked for |

The part has no reset pin, so those survived every reboot, and the
driver's probe merged bits instead of writing bytes, so it never
cleared them. **INT_INVERT matters most to the lines above**: with it
set the interrupt is active low while the overlay asks for level high,
so the three events arrived through an interrupt configured the
opposite way round from the description the kernel was given. They
arrived, and the path is proven end to end; the polarity under them was
not what the device tree says.

The run should be repeated once the probe writes those registers whole.
Journal section 18.

## What produced it

    echo 1 > events/in_accel_x\|y\|z_gesture_singletap_en
    echo 1 > events/in_accel_x\|y\|z_gesture_doubletap_en
    echo 1 > events/in_accel_x\|y\|z_thresh_falling_en
    iio-events bench-adxl345 -t 20

The threshold was the probe default, `0x30`, which is 3 g at 62.5 mg
per count. A tap on the bench surface reached it; a finger on the
breakout had not, in an earlier run with the same settings.
